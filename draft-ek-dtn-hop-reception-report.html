Bundle Protocol Hop Reception Reports

Abstract

This document defines the Hop Reception Report Request block, a Bundle Protocol version 7 (BPv7) extension block by which a forwarding node requests that the next-hop node report reception of the bundle back to it. The request is addressed implicitly, using the node ID already carried in the bundle's Previous Node block. This document also defines the Hop Reception Report administrative record, which batches positive reception assertions for one or more bundles or fragments for the same requesting neighbor. These reports do not transfer custody or responsibility for the reported bundles.¶

1. Introduction

When a Bundle Protocol version 7 (BPv7) [RFC9171] node forwards a bundle to a neighboring node, the Convergence Layer Adapter (CLA) it uses can typically indicate that the transfer completed. That indication, however, reflects only what the convergence layer or underlying transport can observe: that the data reached the peer's convergence layer (or, in some cases, only the peer's transport stack). It does not indicate that the peer's Bundle Protocol Agent (BPA) has received the bundle. If the peer's convergence layer or BPA fails between transport-level receipt and BPA processing, the bundle may be lost while the forwarding node believes it was successfully transferred.¶

BPv7 provides Bundle Status Reports ([RFC9171], Section 6.1.1) as a mechanism for nodes to report the reception, forwarding, delivery, or deletion of a bundle. However, whether reports are requested, and where they are sent, is determined solely by the bundle's source via the primary block, which is immutable after creation. A source can request reception reports from nodes along the path, subject to their reporting policies, but a forwarding node cannot use those primary-block flags to request a report for its own purposes.¶

This document defines the Hop Reception Report Request block, an extension block that a forwarding node inserts to request that the next-hop node send a reception report back to the forwarding node. The block carries no addressing information of its own: the report is sent to the validated node ID in the bundle's Previous Node block ([RFC9171], Section 4.4.1). The response uses a new administrative record type, Hop Reception Report, containing a nonempty batch of positive reception assertions. Ordinary Bundle Status Reports are already administrative records; the new type provides different content and batching semantics, rather than changing the administrative-record flag on an ordinary status report. The request remains an extension block in the subject bundle, not a separate administrative-record exchange.¶

The resulting signal, "the next-hop BPA has received this bundle", has exactly the meaning of the "reporting node received bundle" status assertion of [RFC9171], Section 6.1.1. That assertion is generated at Step 2 of [RFC9171], Section 5.6, before subsequent validation. It does not establish successful later validation, completion of all reception processing, durable storage, custody, forwarding, delivery, or continued retention. It is an explicit BPA-level indication independent of the convergence layer, not a claim that every convergence-layer completion indication is weaker. How a forwarding BPA uses this signal is a matter of local policy and is outside the scope of this document. In particular, this document does not define a custody transfer mechanism, and the report does not transfer any responsibility for the bundle between nodes.¶

"One hop" describes the reception event and the requesting neighbor. Supporting receiving nodes remove the request block before onward forwarding, and the required block processing control flags cause non-supporting nodes to discard it. Addressing the report carrier bundle to the requesting neighbor does not constrain its route to the immediate link. Return routing is a matter of local policy.¶

3. Hop Reception Report Request Block

3.1. Block Definition

The Hop Reception Report Request block is a BPv7 canonical block with a block type code of TBD1 (see Section 9).¶

The block-type-specific data of the block SHALL be a single CBOR unsigned integer [RFC8949] representing a flags field. No flags are defined by this document; the value SHALL be zero (0) when emitted, and receiving nodes SHALL ignore any flag bits they do not recognize.¶

The block SHALL NOT appear more than once in a bundle.¶

3.2. Dependence on the Previous Node Block

The Hop Reception Report Request block has meaning only in conjunction with a Previous Node block ([RFC9171], Section 4.4.1), which identifies the node to which the reception report is to be sent. A bundle containing a Hop Reception Report Request block but no Previous Node block MUST be treated by the receiving node as if the Hop Reception Report Request block could not be processed (see Section 5.2).¶

Because the Previous Node block is itself replaced at each hop, the addressing of the request follows the bundle's actual path without the forwarding node needing to place its own node ID in the request block.¶

3.3. Block Processing Control Flags

A forwarding node inserting the Hop Reception Report Request block SHALL set the block processing control flags ([RFC9171], Section 4.2.4) as follows. These flags are distinct from the zero-valued flags field in the block-type-specific data.¶

  • "Block must be replicated in every fragment" (bit 0): SHOULD be set to 1, so that a node receiving only a fragment can report reception of that fragment. Hop Reception Report entries carry fragment offset and payload length, so distinct fragments are distinguishable.¶

  • "Transmit status report if block can't be processed" (bit 1): MUST be 0.¶

  • "Delete bundle if block can't be processed" (bit 2): MUST be 0. Inability to honor a conforming request does not require deletion of its bundle.¶

  • "Discard block if it can't be processed" (bit 4): MUST be 1, so that a node that does not implement this specification removes the block before forwarding the bundle further, preserving the one-hop scope.¶

4. Hop Reception Report Administrative Record

The Hop Reception Report is a BPv7 administrative record with record type code TBD2 (see Section 9), distinct from ordinary Bundle Status Report type 1. It SHALL use the two-element CBOR administrative-record envelope of [RFC9171], Section 6.1, as updated by [RFC9713]:¶

[TBD2, [reception-entry, ...]]
¶

The record content SHALL be an array containing at least one reception entry. A batch MAY contain any positive number of entries within applicable bundle-size and implementation limits; this specification imposes no fixed protocol maximum and does not require unbounded resources. Each entry positively asserts reception of the identified bundle or fragment. Omission of an identifier conveys no negative assertion. The record has no status indicators, ordinary Bundle Status Report status arrays, or reason codes, and conveys no custody, refusal, forwarding, delivery, or deletion status.¶

Each entry SHALL be an array containing a bundle identifier and, when required below, a reception time. The identifier SHALL be an array of two items for a non-fragment: its source node ID and creation timestamp. For a fragment it SHALL instead contain four items: the source node ID, creation timestamp, fragment offset, and fragment payload length, in that order. Fragment offset and payload length MUST appear together, and MUST appear if and only if the subject bundle is a fragment. Offset zero does not mean "not a fragment". The length is the length in bytes of the received fragment's payload, not the total ADU length.¶

Source node IDs SHALL use the applicable BP EID encoding of [RFC9171], Section 4.2.5 and the referenced URI scheme specification; the null endpoint ID is not permitted. Creation timestamps SHALL use [RFC9171], Section 4.2.7. Fragment offsets and payload lengths SHALL be CBOR unsigned integers. Reception times SHALL be DTN times as defined in [RFC9171], Section 4.2.6, including its zero value for unknown time.¶

An entry MUST include a reception time if the subject bundle's "Report status time" bundle processing control flag is set, and MUST omit it otherwise. This is the reception event's time as reported by the receiving node's local clock, not the time of batch creation or transmission. A batch MAY mix entries with and without reception times, and MAY contain different source node IDs and creation timestamps. All entries MUST concern requests from the same validated previous-hop node, which is the recipient of the carrier bundle. The reporting and requesting node IDs are carried by that bundle, not repeated in each entry.¶

4.1. CDDL

The following CDDL [RFC8610] defines the record structure. TBD2 is a symbolic placeholder for the single record type code to be allocated by IANA. Its temporary definition as uint makes the CDDL usable before allocation; it does not permit arbitrary record type codes on the wire. The EID rule describes the common BP EID structure; its scheme-specific part MUST additionally conform to the applicable URI scheme encoding, and the EID MUST identify a non-anonymous source node. The relationship to the subject bundle's fragment and status-time flags is specified in Section 4 and cannot be checked from the record structure alone.¶

hop-reception-report = [TBD2, reception-batch]
TBD2 = uint ; Replace with the allocated unsigned integer literal.

reception-batch = [1* reception-entry]
reception-entry = [bundle-id, ? reception-time]

bundle-id = [source-node-id, creation-timestamp]
          / [source-node-id, creation-timestamp,
             fragment-offset, fragment-payload-length]

source-node-id = [uri-scheme-code: uint, scheme-specific-part: any]
creation-timestamp = [creation-time: dtn-time, sequence-number: uint]
dtn-time = uint
reception-time = dtn-time
fragment-offset = uint
fragment-payload-length = uint
¶

5. Node Processing

5.1. Forwarding Node

A node MAY insert a Hop Reception Report Request block into a bundle when it forwards the bundle to a neighboring node. The decision to do so is a matter of local policy, which MAY take into account the bundle's characteristics, the identity of the next hop, and the convergence layer in use.¶

When inserting the block, the forwarding node MUST also ensure the bundle contains a Previous Node block whose node ID identifies the forwarding node, as required by [RFC9171], Section 4.4.1. A node MUST NOT insert a Hop Reception Report Request block into a bundle that does not, or will not, contain a Previous Node block.¶

A node MUST NOT insert a Hop Reception Report Request block into a bundle whose payload is an administrative record, or whose source node ID is the null endpoint ID. This parallels the restrictions on status report request flags in [RFC9171], Section 4.2.3 and prevents reception reports from themselves generating reception reports.¶

If a bundle received by the node already contains a Hop Reception Report Request block that was not removed (for example, because the node received the bundle from a node that does not implement this specification and did not honor the "discard block" flag), the node MUST remove it before inserting its own.¶

5.2. Receiving Node

Upon receiving a bundle containing a Hop Reception Report Request block, a node that implements this specification SHALL associate the request with the reception event at Step 2 of [RFC9171], Section 5.6, at which a source-requested reception status report would be generated. The node MUST check the following before honoring the request:¶

  1. The bundle contains exactly one Hop Reception Report Request block, with the structure specified in Section 3 and the required block processing control flag settings in Section 3.3. Unrecognized bits in the block-type-specific flags field are ignored as specified in Section 3.¶

  2. The subject bundle is neither an administrative-record bundle nor an anonymous-source bundle. A node MUST NOT generate a Hop Reception Report in response to a Hop Reception Report, even if a request block is present.¶

  3. The bundle contains exactly one well-formed Previous Node block with a valid node ID.¶

  4. The Previous Node ID identifies the actual convergence-layer peer from which this bundle was received. The node MUST establish this correspondence through peer authentication or trusted configuration; absent that association, it MUST NOT honor the request (Section 8).¶

  5. The subject bundle's identifier and status-time flag can be determined in accordance with Section 4.¶

These are request validity and eligibility checks, not an assertion that all subsequent reception validation has succeeded. The node MUST capture the requesting node ID, the subject bundle or fragment identity, the status-time flag, and, when required, the reception event's time before reassembly or replacement or removal of hop-specific blocks. Deferring request checks or batch construction MUST NOT change the event being reported or replace its timestamp with the time of those later actions.¶

Local policy MAY permit honoring an otherwise valid request; it cannot make an invalid request valid. For each request it honors, the node SHALL create a pending reception entry as specified in Section 4, for aggregation and reporting according to Section 5.3. It MUST NOT delay processing or forwarding of the subject bundle while waiting to fill a batch.¶

If a request is invalid, the node MUST NOT create a reception entry for it. The node SHALL treat the request block as one that cannot be processed, subject to the malformed-block and unprocessable-block rules of [RFC9171], Section 5.6. A policy decision to decline an otherwise valid request does not itself invalidate or delete the subject bundle.¶

Whether the request is honored, declined, or invalid, a supporting node MUST remove all received Hop Reception Report Request blocks before onward forwarding, regardless of their "Discard block if it can't be processed" flags. The node MAY insert its own new request as described in Section 5.1. Ordinary source-requested status reporting remains independent (Section 6.1).¶

5.3. Batching and Scheduling

A reporting node MUST batch only pending entries with the same validated recipient node ID and compatible security treatment. Compatibility means that the carrier's authentication, integrity, confidentiality, and security-policy context satisfy the requirements for every entry; batching MUST NOT weaken protection required for any entry. Different subject source EIDs and creation timestamps do not prevent batching. Single-entry reports are permitted.¶

Implementations MUST provide configurable finite bounds on pending reporting state, batch size (entry count and encoded size), and maximum aggregation delay. Size limits MUST account for the carrier bundle and its security overhead within applicable bundle-size limits. These are local resource limits, not fixed protocol maxima. The aggregation delay for an entry begins when the pending entry is created; adding entries MUST NOT postpone an older entry's deadline.¶

Unless pending state is discarded under the resource policy below, a node MUST flush pending entries into one or more report carrier bundles when an applicable size or count threshold is reached, when the maximum aggregation delay is reached, or when an appropriate return-contact opportunity occurs. A flush ends aggregation for those entries and makes the resulting reports available to the local transmission scheduler. Expiration of the aggregation delay does not guarantee immediate transmission over an unavailable contact. A node MAY flush earlier, including immediately for a single entry.¶

Under resource pressure, local policy MAY decline new requests or discard pending reporting state, including entries previously created for honored requests. Neither action changes processing of the subject bundle or creates a negative reception assertion. Reporting state and queued report bundles need not be retained without bound.¶

Batching reduces per-report bundle overhead, but increases acknowledgement latency and the number of reception assertions lost with one report bundle. Report lifetime, scheduling, routing, and retry policy are local matters. Report delivery is not guaranteed.¶

5.4. Carrier Bundle Construction

For each batch to be sent, the administrative element SHALL construct one Hop Reception Report administrative record and request transmission of a carrier bundle as in [RFC9171], Section 6.2. The carrier's payload SHALL contain exactly that one record, including its two-element envelope and nonempty batch. The carrier bundle's source node ID MUST identify the reporting node, and its destination MUST be the validated requesting node ID shared by all entries. Those identities MUST NOT be added to each entry.¶

The carrier MUST have the "ADU is an administrative record" bundle processing control flag set and MUST comply with the administrative-bundle restrictions of [RFC9171]. In particular, all status report request flags MUST be zero (Section 4.2.3), and the "Transmit status report if block can't be processed" flag MUST be zero in every canonical block (Section 4.2.4). The carrier MUST NOT contain a Hop Reception Report Request block. Its destination identifies the requesting neighbor but does not restrict the return route to a single link.¶

5.5. Report Recipient Processing

The receiving administrative element MUST validate the complete Hop Reception Report record before applying any entry. This includes the two-element envelope and supported record type, a nonempty batch, every entry's structure and field encodings, and the paired fragment fields. An empty batch, incomplete fragment identity, or malformed entry invalidates the entire record; a valid prefix MUST NOT be applied.¶

As required by [RFC9713], Section 2, a not-well-formed administrative record ADU or a record type that the element cannot process SHALL be ignored. Records that violate this specification's format MUST likewise be ignored. This does not undo delivery of the carrier bundle or change its BPA processing. Implementations MAY impose resource limits when validating records, but MUST NOT partially apply a record they could not validate completely.¶

The recipient MUST correlate each entry with locally tracked transmissions of the identified bundle or fragment to the reporting neighbor identified by the carrier's source node ID. Before using a report for consequential retention or retransmission decisions, the recipient MUST establish the reporting node's identity and the integrity of the reported entries as described in Section 8. A bundle source field alone is not authentication.¶

Duplicate assertions, within or across reports, MUST be processed idempotently. Unknown identifiers MUST NOT acknowledge other bundles or fragments; the recipient MAY ignore such entries without invalidating otherwise useful entries in the validated record. Where locally tracked subject information is available, an entry inconsistent with that subject's fragment identity or required timestamp presence MUST NOT be used to acknowledge it. Identifiers name bundles or fragments, not individual retransmission attempts: a delayed or replayed assertion cannot establish which attempt was received, or that the reporting node still retains the bundle.¶

5.6. Interaction with Fragmentation

If a node fragments a bundle containing a Hop Reception Report Request block, the block is replicated in each fragment when bit 0 of its block processing control flags is set, as recommended in Section 3.3. Each honored fragment request creates an entry carrying that received fragment's identity, including its offset and payload length. Multiple such entries MAY be batched together if they meet Section 5.3, even if their fragments are subsequently reassembled.¶

The node MUST capture the requester and fragment identity before reassembly or replacement or removal of hop-specific blocks, as required in Section 5.2. Reassembly MUST NOT substitute a non-fragment identifier for a bundle that was not received in that form. A report acknowledging one fragment does not acknowledge the entire original bundle, and fragments received from different requesting nodes cannot be combined in a batch addressed to just one of them.¶

6. Relationship to Other Mechanisms

6.1. Bundle Status Reports

This document does not alter the Bundle Status Report format or the conditions under which the primary block's status report request flags cause reports to be generated. Ordinary source-requested reporting remains unchanged and independent of Hop Reception Reports. The two mechanisms use different administrative record types, even when their destinations coincide. An ordinary Bundle Status Report does not satisfy a hop request, and a Hop Reception Report does not satisfy a source-requested status report.¶

The traffic concerns of [RFC9171], Section 5.1 also apply here. Hop Reception Report generation MUST be disabled by default and enabled only when the risk of excessive traffic is deemed acceptable. Each honored request creates a pending entry, not necessarily a separate report bundle. Batching amortizes carrier overhead across entries, but requests still consume processing, storage, and return-path capacity. The forwarding node controls when it requests reports, while the reporting node controls whether to honor requests and how to aggregate and schedule reports. Return traffic need not use the immediate link.¶

6.2. Custody Transfer

This document does not define custody transfer. It provides a forwarding node with a positive indication that the next hop's BPA has received a bundle, nothing more. The report does not signify that the receiving node has undertaken to forward, deliver, or retain the bundle, and the receiving node incurs no responsibility toward the bundle beyond that which it would have under [RFC9171] absent this block. What the forwarding node does with the indication is local policy.¶

6.3. Convergence Layer Completion Indications

Convergence layer specifications typically define a "transmission success" indication to the BPA. Hop Reception Reports complement such indications, not replace them, by providing an explicit BPA-level reception assertion independent of the convergence layer in use.¶

Even when the convergence layer indicates success, absence of a report does not distinguish non-support from transfer failure. Silence can also result from policy refusal, discarded reporting state, pending aggregation, an unavailable return contact, receiver failure, or report loss. Neither silence nor omission of an entry is a negative assertion about reception.¶

8. Security Considerations

8.1. Reflection

A mechanism that causes a node to send a message to a third party on request is a potential reflection vector: an attacker able to inject a bundle carrying a Hop Reception Report Request block and a Previous Node block naming a victim could cause the receiving node to send a report to the victim.¶

The validity condition in Section 5.2, that the Previous Node block's node ID must identify the convergence-layer peer from which the bundle was actually received, is the primary mitigation. Over convergence layers that authenticate the peer node ID, such as TCPCLv4 [RFC9174] with certificate-based node identification, that authentication can establish the association. Otherwise, trusted configuration (for example, a configured peer identity on a controlled link) MUST establish it. A node MUST NOT honor the request if neither method establishes the association. Request authentication does not waive the actual-peer association check, and local policy MAY decline even a valid request.¶

Addressing a report to the previous hop does not confine its route or reflection costs to the immediate link. Return routing is local policy, and authorization, rate limits, and resource bounds remain necessary even for authenticated requesting peers.¶

8.2. Integrity and Reporter Authentication

The Hop Reception Report Request block and the Previous Node block are inserted by the forwarding node and can be integrity-protected by that node using a Block Integrity Block [RFC9172] with a security source of the forwarding node. A receiving node with a security association with the forwarding node can thereby verify that the request was placed by that node. A source-applied Block Integrity Block cannot cover these blocks, since they did not exist at the source. Removal or replacement of hop-specific blocks needs to respect applicable BPSec processing rules.¶

Authenticating the request does not authenticate the response. A forged or modified report could induce premature deletion of a retained copy or suppression of needed retransmission. Before making consequential retention or retransmission decisions, the report recipient MUST establish the reporting node's identity and the integrity of all entries it uses, including their binding to that identity. Protection can use BPSec with an appropriate security context and trust policy covering the report payload and binding the carrier's source identity. Security requirements for all entries must be compatible before batching (Section 5.3).¶

An authenticated and integrity-protected direct convergence-layer exchange can provide this assurance when the authenticated peer is the reporting node and the exchange protects the report. On a multihop return path, authenticating the last transport peer does not authenticate the original reporter or protect the entries against modification by earlier nodes. Such paths require protection and trust arrangements that establish the original reporter's identity and the integrity of its assertions; the carrier source field alone is insufficient. When bundle-layer security services are needed, they SHALL use BPSec as required by [RFC9171], Section 8. Authentication establishes who made an assertion, not that a dishonest reporter actually received or retained the subject.¶

8.3. Replay and Duplicates

A valid report can be duplicated or replayed. Recipients MUST apply assertions idempotently and correlate them with locally tracked bundle or fragment identities and the reporting neighbor (Section 5.5). Neither a bundle identifier nor an optional reception time identifies an individual retransmission attempt. A replayed report is not evidence of a new reception or continued retention. Local policy needs to account for stale reports, bounded correlation state, and the limitations of clocks when deciding whether an assertion is useful. This specification adds no sequence-number or anti-replay exchange.¶

8.4. Resource Exhaustion and Correlated Loss

Requests can consume pending-state storage, encoding work, security processing, and return-path capacity, even when peers are authenticated. Large received batches also consume validation and correlation resources. Nodes SHOULD apply per-peer rate limits and resource budgets in addition to the configurable limits in Section 5.3. Policy refusal and discarding pending state are preferable to allowing reporting to exhaust resources needed for subject-bundle processing. A request does not guarantee a report, and a refusal is not encoded as a negative entry.¶

Loss or suppression of one batched report removes multiple assertions at once. This correlated loss can cause bursts of unnecessary retransmission if local policy reacts to silence. Batch-size and delay limits, report scheduling, and retransmission policies should account for this tradeoff rather than treating each missing entry as an independent transfer failure.¶

8.5. Traffic Analysis

Reports expose bundle identifiers and, when requested, reception times. A batch can link traffic from different sources through a common forwarding and reporting relationship; its size, membership, and timing can reveal traffic volumes and contact patterns. Aggregation also means that report transmission timing is not simply the reception event time.¶

Convergence-layer confidentiality, such as TCPCLv4 with TLS, protects content on the links where it is used, but does not hide all traffic metadata or protect content from intermediate nodes on a multihop return path. BPSec payload confidentiality can protect entries across that path, while carrier addressing, sizes, and timing may remain observable. Confidentiality policies for different subjects must not be weakened by placing them in a common batch.¶
